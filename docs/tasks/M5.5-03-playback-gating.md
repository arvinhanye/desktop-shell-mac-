## 目标

只有别的应用在放声音时才开系统音频捕获，省掉探针测到的"捕获期间 `coreaudiod` 多耗约 3% 单核，安静时也一样"。有应用开始放声音时立刻开始捕获；所有应用都停止输出 3 秒后拆掉。

## 背景与约束

- AGENTS.md："省电要求"（没有应用在放声音时不开捕获，停止前等 3 秒）；"技术探针"里的播放检测探针。下面把探针结论再列一遍，方便对照。
- **Claude Code 的探针**（2026-10-19，命令行小程序，不需要任何权限）：
  - **能拿到**：不开捕获，也能知道哪些进程正在输出声音。系统对象的 `kAudioHardwarePropertyProcessObjectList`（macOS 14.2 起）列出所有用过音频的进程，每个进程对象可以读到 `kAudioProcessPropertyPID` 和 `kAudioProcessPropertyIsRunningOutput`。
  - **事件要监听 `IsRunning`**：进程开始或停止输出时，进程对象发的是 `kAudioProcessPropertyIsRunning`（`pir?`）和 `kAudioProcessPropertyDevices`（`pdv#`），**不发** `kAudioProcessPropertyIsRunningOutput` 本身。直接监听 `IsRunningOutput` 一个事件都收不到。所以要监听 `IsRunning`，收到后再去读 `IsRunningOutput`。
  - **新进程要立刻读一遍**：新进程出现时可能已经在输出了。`afplay` 实测：列表变化的那一刻它已经在输出，之后没有单独的事件。所以进程列表变化时，要重新读全部进程的状态。
  - **事件情况**：
    - 进程列表的事件常常连着来两次。
    - 一个常驻进程（AVAudioEngine）开、关输出两轮，每次都在约 0.05 秒内收到事件。
    - 音量为 0 的播放也算"在输出"。
  - **不用设备级属性**：默认输出设备的 `kAudioDevicePropertyDeviceIsRunningSomewhere` 也能反映有没有声音，但开着捕获时，聚合设备包含输出设备，这个属性很可能被我们自己占住，所以不用它。
- 本进程自己不放声音：背景视频没有音轨。点头像的语音由 WebKit 的进程播放，不是本进程，所以会触发捕获，这正是想要的。为了保险，仍然排除本进程的 PID。

### 1. 播放检测（新建 `Sources/DesktopShell/PlaybackMonitor.swift`）

```swift
@MainActor
final class PlaybackMonitor {
    var onChange: ((Bool) -> Void)?   // 别的进程有没有在输出声音
    private(set) var othersPlaying: Bool
    func start()
    func stop()
}
```

- **监听**：
  - 在系统对象上监听 `kAudioHardwarePropertyProcessObjectList`。
  - 对列表里的每个进程对象监听 `kAudioProcessPropertyIsRunning`。
  - 列表变化时，给新出现的进程加监听，给消失的进程去掉监听。`AudioObjectRemovePropertyListenerBlock` 要传加监听时的同一个 block 和队列，所以要把它们存起来。
- **判断**：
  - 收到任何事件，都在主线程把全部进程重新读一遍：有没有 PID 不是本进程、并且 `IsRunningOutput == 1` 的进程。
  - 结果变化时回调 `onChange`。
  - 连着来的事件可以合并，主线程同一轮只算一次。
  - `start()` 时先读一次初始状态。
- **纯函数**：`func anyOtherOutputting(_ processes: [(pid: pid_t, runningOutput: Bool)], ownPID: pid_t) -> Bool`，写单元测试。
- **日志**：启动时记一行初始状态，之后变化时各记一行：`DesktopShell audio: playback=true` / `playback=false`。

### 2. 并进捕获的条件（`AudioSpectrum.swift`、`AppDelegate.swift`）

- **条件**：捕获的条件改成"没暂停，**并且**别的进程在输出声音"。
- **开始**：条件变真时立刻搭建。
- **停止**：
  - 暂停时立刻拆除。
  - 别的进程都停止输出后，要**持续 3 秒**才拆除，切歌的间隙不会反复搭了又拆。3 秒内又有输出就取消。
  - 用一次性的延迟任务实现，不轮询。可以参考 `OcclusionDebouncer` 的写法，但不要改 `OcclusionDebouncer.swift` 本身。
- **日志**：新增停止原因 `reason=noPlayback`。
- **接线**：`AppDelegate` 创建 `PlaybackMonitor`，把 `onChange` 接到 `AudioSpectrum`，退出时调用 `stop()`。
- **测试**：给 M5.5-02 的状态机加上这个输入，补以下测试：
  - 没暂停但没人放声音 → 不搭建。
  - 有人放声音 → 搭建。
  - 停止输出后 2.9 秒内又开始 → 不拆除。
  - 停止输出满 3 秒 → 拆除。
  - 暂停时有人放声音 → 不搭建。
  - 暂停取消时有人在放 → 立刻搭建。
- **已知限制**（写进代码注释）：有的应用暂停播放后，输出流还会开一阵（例如浏览器）。这期间捕获照样开着，但分析器在静音时不做 FFT、不推送。
